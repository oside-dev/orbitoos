## Current state

The connected Supabase project reports 26 applied migrations, ending at `20261013060943_public_function_default_execute_privileges`. The repository tracks all 26 production version/name pairs under `supabase/migrations/`. The latest migration was applied through the connected Supabase project on 2026-10-13; Supabase recorded the exact version/name pair `20261013060943 / public_function_default_execute_privileges`.

A read-only default-ACL audit found that functions created by `postgres` could inherit `EXECUTE` for `PUBLIC` and direct `anon`/`authenticated` grants in `public`. Migration `supabase/migrations/20261013060943_public_function_default_execute_privileges.sql` has now been applied and verified in production. It revokes the global default `PUBLIC EXECUTE` grant for future `postgres`-owned functions and removes the direct `anon`/`authenticated` default grants for future functions in `public`, while retaining `postgres` and server-only `service_role` default execution there. It leaves managed `storage` schema defaults unchanged. Existing application function ACLs were not changed by this migration; a post-apply check confirmed all 17 public application functions remain non-executable by `anon` and `authenticated`, and `private.handle_new_user()` remains non-executable by browser/service roles while its Auth trigger stays enabled.

**Post-apply verification on 2026-10-13:** `pg_default_acl` now has no global `PUBLIC EXECUTE` entry for functions created by `postgres`; the `public` schema default entries contain `postgres` and `service_role`, but no `anon` or `authenticated`. All 21 current application functions still have the expected restricted effective grants.

The latest main validation run passed runtime/security contract tests, browser E2E, and fresh local migration replay in GitHub Actions. A successful local replay proves replayability, not exact schema equivalence to production.

Most restored migrations were recovered from the versioned SQL contracts already stored under `docs/architecture/`. ## Schema parity finding: Auth profile bootstrap trigger

A read-only catalog audit on 2026-10-12 found the live trigger `auth.on_auth_user_created`, calling `private.handle_new_user()`. The function is `SECURITY DEFINER`, sets an empty `search_path`, and inserts a supplementary `public.profiles` row from user metadata with `ON CONFLICT (id) DO NOTHING`. That function and trigger were present in production but were missing from the tracked migration chain and `supabase/schema.sql`, so a newly rebuilt local database could behave differently on Auth signup.

Migration `20261012030454_track_auth_profile_creation_trigger` is now applied to production and tracked in source. It recreates the same function definition and adds the trigger only if the exact trigger/function binding is absent; it fails closed if a trigger with the same name points elsewhere. The live trigger remains enabled. A read-only acceptance refresh on 2026-10-13 confirms one Auth user and one profile row, and confirms that the same user has the expected workspace, owner membership, and default brand. The content creation/persistence flow remains a separate acceptance step.

A follow-up least-privilege audit on 2026-10-13 found PostgreSQL's default function ACL left EXECUTE effective for anon, authenticated, and service_role on this trigger helper. Migration `20261013050901_restrict_auth_profile_trigger_execution` is applied in production and tracked in source at the exact recorded version. It revokes EXECUTE from PUBLIC, anon, authenticated, and service_role, then checks the effective ACLs and the trigger/function binding. A read-only post-apply query confirmed EXECUTE is false for anon, authenticated, and service_role, and the Auth trigger remains enabled. The migration history now records 25 applied versions.

## Security finding: excessive table-level grants

A read-only production catalog query on 2026-10-11 found effective `TRUNCATE`, `REFERENCES`, and `TRIGGER` privileges for both `anon` and `authenticated` on `activities`, `api_logs`, `notifications`, and `plans`. The `authenticated` role also had those table-level privileges on the optional legacy `profiles` table. RLS was enabled, and the inspected row policies were scoped to workspace membership, the signed-in user, or active plans, but **RLS does not protect a table from `TRUNCATE`**. The broad default grants therefore did not follow the intended row-level security boundary.

The production migration `20261012022853_restrict_unsafe_legacy_table_privileges` revokes browser-role table grants on those five tables, then restores only the operations supported by existing policies: workspace-scoped CRUD for activities and notifications; SELECT/INSERT/DELETE for API logs; SELECT-only active plan access; and self/workspace-scoped profile access. It also revokes broad default table and sequence privileges for `anon` and `authenticated` on future objects created by the application migration role (`postgres`) in `public`. Explicit `service_role` permissions are retained.

**Post-apply verification on 2026-10-12:** a read-only query confirmed that RLS remained enabled and effective `TRUNCATE`, `REFERENCES`, and `TRIGGER` privileges were false for both browser roles on all five tables. The `postgres` default ACL entries for new `public` tables and sequences no longer list `anon` or `authenticated`. The application tables inspected are owned by `postgres`. The managed `supabase_admin` role still has its own broad default ACL entry; it was not changed because that superuser may be used by Supabase-managed operations. Revisit only after a separate compatibility assessment identifies whether application objects are ever created under that role.

The first acceptance attempt observed `bootstrap-workspace` returning HTTP 401 after the Auth user/profile rows were created. That observation is now superseded by a read-only production check on 2026-10-13: there is one Auth user, one profile, one workspace, one owner membership, and one default brand. Each row matches the deterministic `workspace-<user>`, `membership-<user>`, and `brand-default-<user>` bootstrap pattern. Edge Function `bootstrap-workspace` is ACTIVE at version 4, and its deployed source matches `main`; the current handler resolves the user from `ctx.userClaims.id` with a fallback to JWT `sub`. Workspace provisioning is therefore confirmed from the live catalog. The remaining acceptance is the real signed-in product flow—create an idea, edit a content variant, reload, and verify persistence—because production still has zero ideas, content items, content variants, schedules, social accounts, and publishing jobs. Keep publishing and token-refresh feature switches disabled until that content-flow acceptance and operator-controlled Meta setup are complete.

## Read-only core-schema parity checkpoint — 2026-10-13

A follow-up catalog comparison was run against the connected production project `lkcbtgqdvzmaihcnxxwk` without changing database state.

- The canonical `supabase/schema.sql` plus the tracked expansion/alter migrations were compared against the live `public` and `private` table catalog.
- All **24** live application tables had a matching tracked source table definition.
- All **243** live application columns matched a tracked source column by table and column name. Data types also matched after normalizing PostgreSQL's `timestamptz` alias to `timestamp with time zone`.
- For the 11 canonical core tables, all **39** tracked RLS policy names/commands/roles were found live, with no extra policy names in that subset.
- A wider policy inventory found **64** live policies across `public` (58) and `private` (6). All 64 have matching tracked source policy definitions by schema/table/name, permissive mode, command, and target roles; no live policy was missing from source inventory. This read-only inventory did **not** prove semantic equivalence of every `USING`/`WITH CHECK` expression; full predicate-level parity remains open.
- A read-only index-definition comparison covered all **84** live indexes (**74** in `public`, **10** in `private`). All **53** explicit non-constraint indexes matched tracked `CREATE INDEX` definitions by table, uniqueness, key columns, and predicate after normalizing whitespace, schema qualification, and PostgreSQL's emitted type casts. The three partial indexes — `publishing_jobs_due_idx`, `publishing_jobs_expired_lease_idx`, and `schedules_materialization_idx` — have the same predicate conditions; PostgreSQL's deparser adds an explicit `::text` cast and extra parentheses around the string comparison. The remaining **31** indexes are backing indexes for tracked `PRIMARY KEY`/`UNIQUE` constraints. All **84** indexes are `valid` and `ready`; no expression indexes or invalid/not-ready indexes were found.
- All **four** non-internal triggers found on application/Auth tables matched the tracked trigger inventory: `auth.users.on_auth_user_created`, `private.social_account_secrets_cleanup_vault`, and the two content approval role-guard triggers. All four were enabled. Their source definitions are present in the tracked migration chain.
- The live catalog contains **21** unique application functions across `public` and `private`; a source inventory of `supabase/schema.sql` and all 26 migrations contains the same 21 names.
- The body of each of the **21** live functions was compared to the latest matching `CREATE OR REPLACE FUNCTION` body in the tracked migration chain (using `supabase/schema.sql` only when a migration source was absent). All **21/21 bodies matched exactly**, after normalizing line endings and leading/trailing whitespace only.
- Argument signatures match across all **21/21** functions after normalizing PostgreSQL's `timestamptz` alias to `timestamp with time zone`. Return types, `SECURITY DEFINER` versus invoker mode, volatility metadata, and empty `search_path` configuration also matched for **21/21** functions.
- Separate live privilege checks confirmed `private.handle_new_user()` has no effective `EXECUTE` for `anon`, `authenticated`, or `service_role`, while its Auth trigger remains enabled. The current catalog also shows all `public` SECURITY DEFINER functions have explicit ACLs restricting execution to `postgres`/`service_role`; `private.user_workspace_ids()` is executable by `authenticated` for policy use. A full source-to-catalog comparison of every function/table grant and default ACL remains open.

This is a **partial parity checkpoint**, not proof of full schema equivalence. Still open are expression-level comparison of all defaults, exact check/FK constraint semantics, RLS predicate equivalence on every table, complete effective grants/default ACLs, extension configuration, and scheduler/Vault definitions.
